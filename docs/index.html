Lost in the Flow with Code Talkers

Chang Shi Ying, Chiok Yew Ho, Yichen Li, and Yintong Huo

Instruction tuning makes code models better at command-style interaction, but the paper shows that the gain is not free: infilling degrades, completion changes benchmark by benchmark, and generation behavior becomes more verbose and less tightly bounded.

Flow mode

Completion and infilling inside unfinished code

The paper treats localized continuation as a distinct cognitive mode where developers expect short, bounded, structure-aware suggestions.

Command mode

Natural-language intent to executable code

Instruction tuning is designed for this setting, where the model must infer and follow developer intent expressed in natural language.

Main claim

The Instruction-Tuning Tax

Instruction tuning reallocates capability. It helps some task modes, but it can weaken infilling and alter generation behavior in ways that matter for real coding assistants.

Motivation

Programming has two cognitive modes

The paper argues that code assistants serve developers in two different ways, and those modes demand different model behavior.

Flow

Stay inside the code and keep momentum

Developers are extending an existing thought process. They need code completion or fill-in-the-middle suggestions that respect the local prefix, suffix, and surrounding structure.

  • Code completion
  • Fill-in-the-middle infilling
  • Short, bounded, syntax-aware continuations
Command

Step back and describe intent in natural language

Developers articulate what they want. The model should understand the instruction and synthesize code that follows the described goal or specification.

  • Instruction following
  • Natural-language to code generation
  • Preference alignment and assistant-like behavior

Study design

What the paper evaluates

The study compares matched base and instruct models, then combines benchmark performance, failure analysis, and checkpoint evolution to understand what instruction tuning changes.

Model families

Two open-source CodeLLM families with matched base and instruct variants.

  • Qwen2.5-Coder: 1.5B, 7B, 14B, 32B
  • DeepSeek-Coder: 1.3B, 6.7B, 33B

Task categories

Flow-mode tasks emphasize local structure, while command-mode tasks emphasize instruction understanding.

  • Infilling: HEFIM, SAFIM, ClassEval-LineInfilling
  • Completion: ClassEval-Completion, BigCodeBench-Complete
  • Instruction following: DS-1000, HumanEval, MBPP, BigCodeBench-Instruct

Research questions

The paper moves from headline performance into causes and evolution.

  1. RQ1: How do base and instruct models differ on representative tasks?
  2. RQ2: What behavioral shifts explain those differences?
  3. RQ3: How do capabilities change over the tuning trajectory?

Findings

What the paper argues

The results are not simply "base bad, instruct good" or the reverse. The paper shows a task-dependent capability trade-off and treats it as a deployment problem, not just a leaderboard result.

01

Infilling shows the tax most clearly

Base models retain stronger fill-in-the-middle behavior, and the loss after instruction tuning appears consistently across representative infilling settings.

02

Completion often rises, but not uniformly

Instruct models often benefit from guidance-heavy or docstring-shaped completion tasks, but the gain depends on the benchmark and weakens in later tuning stages.

03

Instruction following improves most clearly

The command-mode upside is real. Later tuning stages strengthen instruction-oriented behavior even when they do not uniformly improve other forms of code generation.

04

Capability is reallocated, not uniformly improved

The paper's conclusion is that instruction tuning is not a free lunch. It shifts model strengths across task types rather than simply making code models better at everything.

RQ2

Behavior shifts, not just benchmark scores

RQ3

Tuning reallocates capability over time

The checkpoint analysis in the manuscript shows that capability changes are non-monotonic. Instruction following rises, infilling slips, and completion stays positive on average but loses momentum in later stages.

Discussion

Why the paper matters

The takeaway is not only about accuracy. It is about how coding assistants should be trained, selected, and safeguarded for different developer workflows.

For researchers

  • Instruction-tuning tax appears model-specific, not universal.
  • Future post-training should preserve concise, boundary-aware continuation for flow-mode tasks.
  • Behavior metrics matter because the trade-off is visible in how models fail, not only in whether they pass.

For practitioners

  • Do not choose models only from aggregate benchmark scores.
  • Deployment safeguards should target dominant failure modes such as verbosity, NL leakage, or extra code.
  • Routing flow-mode and command-mode tasks may be better than treating "instruct" as a universal upgrade.
